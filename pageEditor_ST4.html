1. User Profile Page

↗ View User Profile ✅ Validation Evidence

HTML Structure

The User Profile page (profile.html) is built on the shared HLTHY template, using the group's global style.css for the header, navigation bar, and footer. The <main> section uses a two-column CSS Grid (.profile-layout) — a controls panel on the left and a live profile output area on the right. The key HTML elements are:

  • <header>, <nav>, <main>, <footer> — standard site template structure
  • <div class="steps-row"> — contains three step indicator buttons using role="tab" and aria-selected for screen reader compatibility
  • <div class="progress-wrap"> — holds the visual progress bar; the inner bar element uses role="progressbar" with aria-valuenow, aria-valuemin, and aria-valuemax attributes updated dynamically by JavaScript
  • <div id="status-msg" aria-live="polite"> — a live region that announces step updates to assistive technology without interrupting the user
  • Three <div class="profile-section"> elements inside the output area — one per step — hidden by default and revealed progressively as steps are completed

CSS Techniques

Page-specific styles are embedded in a <style> block in the <head> and do not conflict with the global CSS:

  • CSS Grid (grid-template-columns: 1fr 1.4fr) creates the side-by-side controls and output layout; a media query collapses this to a single column on screens narrower than 680 px
  • Custom step buttons use border-radius: 20px pill shapes with three visual states — .active (filled green), .done (light border), .skipped (grey) — applied dynamically by JavaScript
  • Progress bar uses a background track (.progress-bar-bg) with an inner fill (.progress-bar-fill) whose width is updated in JavaScript; a CSS transition: width 0.4s ease animates the fill smoothly
  • Reveal animation — the @keyframes fadeSlide animation fades and translates profile sections upward when the .revealed class is added
  • Action buttons — three distinct buttons (Start, Skip, Reset) each have their own colour scheme defined using CSS variables from the global stylesheet

JavaScript Implementation

All interactivity on the User Profile page is driven by JavaScript. The implementation meets all coursework requirements:

  • Variables and objects: A profileData object stores collected answers keyed by step and field name. A completed object (with keys s1, s2, s3, each an array of three booleans) tracks which individual prompts have been answered
  • Functions:
    • runStep(stepIndex) — runs the three prompt() dialogs for a given step, stores answers in profileData, updates the DOM output spans, and reveals the corresponding profile section
    • updateProgress() — counts completed prompts, calculates percentage, updates the progress bar width, the text label, and the ARIA attribute; also applies the correct CSS class to each step button
    • revisitStep(n) — calls runStep(n-1) to allow the user to return to any previously skipped or completed step
    • setStatus(msg) — utility function that updates the aria-live status message element
  • Conditional logic: The start-btn click handler uses Array.findIndex() to find the first incomplete step and runs it; if all steps are complete, a status message is shown instead. Step button classes are set inside updateProgress() using if/else checks on the completed object
  • DOM manipulation: JavaScript updates textContent of nine output <span> elements, adds/removes the .revealed class on profile sections, updates style.width on the progress bar fill, and shows/hides the revisit button row and completion message
  • User control: Users can skip individual prompts by pressing Cancel on any prompt() dialog. The Skip Step button advances past an entire step. The Reset button clears all data and hides all profile sections. The Revisit buttons (shown after the first run) allow users to return to any step and fill in previously skipped answers

Design and Implementation Rationale

The two-column grid layout was chosen to show the controls and the live profile simultaneously, so users can see their profile building in real time without scrolling. The profileData object was used instead of a simple array because named keys (e.g. profileData.step1.name) make the code more readable and easier to extend. Native prompt() dialogs were used as required by the coursework specification; they are browser-managed, inherently keyboard-accessible, and require no additional HTML form elements.

2. Sitemap

↗ View Sitemap ✅ Validation Evidence

HTML Structure

The sitemap page (sitemap.html) uses the shared HLTHY template. Inside the <main> section, a <div class="sitemap-wrap"> with overflow-x: auto ensures the SVG scrolls horizontally on small screens without breaking the page layout. The SVG itself is placed directly in the HTML — it is not an image file. Key structural choices:

  • The <svg> element uses width="100%" and viewBox="0 0 860 540" to make it fully responsive — it scales proportionally to any screen width
  • role="img" and aria-label on the <svg> describe the diagram as a whole for screen readers
  • Each clickable node is an <a href="..."> wrapping a <g class="smap-node"> group containing a <rect>, two <text> elements, and a <title>
  • All nodes have tabindex="0" to enable keyboard Tab navigation between them
  • A <defs> block defines a reusable arrowhead marker (id="arr") applied to connector lines using marker-end="url(#arr)"

SVG Hierarchy and Layout

The sitemap represents four levels of hierarchy:

  • Level 1 — Splash Screen: entry point at the top, connected by a solid arrow to the Home page
  • Level 2 — Home Page: central hub, connected by light-green lines to six main pages (Gallery, AIS, Feedback, Team, User Profile, Sitemap)
  • Level 3 — Content Pages: four individual content pages shown below, connected from Home by dashed grey lines to indicate they are secondary content rather than primary navigation destinations
  • Level 4 — Page Editors: grey boxes below each content page, connected by fine lines, representing the footer-linked editor pages

A colour legend at the bottom of the SVG explains the colour coding: dark green for core pages, medium green for secondary pages, muted green for content pages, grey for editor/validation pages, and orange for the current (Sitemap) page node.

CSS Techniques

  • Hover effects: The .smap-node:hover rect rule increases stroke-width to 2.5 and applies filter: brightness(1.08), giving a subtle lightening effect on mouse-over without requiring JavaScript
  • Focus states: .smap-node:focus rect applies an orange stroke (#F4A261 — the site's secondary colour) so keyboard users can see which node is focused
  • cursor: pointer on .smap-node confirms to the user that each node is interactive

Design and Implementation Rationale

The sitemap hierarchy was planned on paper before any code was written, labelling each node's approximate x/y coordinates within the 860×540 viewBox. <polyline> elements with explicit waypoints (rather than straight <line> elements) were used for the Home-to-child connectors so that lines could be routed with L-shaped paths, avoiding overlap with neighbouring nodes. Dashed lines (stroke-dasharray="5 4") distinguish content page connections from primary navigation connections, improving readability of the hierarchy.

3. Content Page — Sleep & Daily Lifestyle

↗ View Content Page ✅ Validation Evidence

HTML Structure

The content page (content_ST4.html) uses the shared HLTHY template. Inside <main>, a .content-layout CSS Grid creates a two-column layout: a sticky sidebar navigation on the left and an <article> containing the main content on the right. The page is divided into five clearly labelled <section> elements, each with a unique id attribute for internal anchor linking:

  • #intro — Overview of sleep and its connection to SDG 3
  • #the-science-of-sleep — Circadian rhythm and sleep pressure
  • #health-benefits — Ten key health benefits of adequate sleep
  • #sleepingtime — Recommended sleep durations by age group
  • #tips-for-sleep — Practical tips for improving sleep hygiene
  • #references — Cited academic and NHS sources

A correct heading hierarchy is maintained throughout: one <h1> for the page title, <h2> for section headings, and <h3> for sub-sections (e.g. Circadian Rhythm and Sleep Pressure within the science section). All five images include descriptive alt text. A fixed-position "Back to Top" button (#go-top) is implemented using position: fixed in CSS with an href="#top" anchor — no JavaScript required.

CSS Techniques

Page-specific styles are defined in an embedded <style> block and include more than five CSS rules as required:

  • CSS Grid (grid-template-columns: 220px 1fr) for the sidebar + article layout, with a media query for single-column on mobile
  • Sticky sidebar (position: sticky; top: 80px) keeps the contents navigation visible as the user scrolls through long sections
  • Hover effect on sidebar links — background and text colour change on hover using CSS variables
  • Content section images — width: 100%; max-height: 360px; object-fit: cover ensures all images are consistently sized regardless of the original image dimensions
  • Go-to-top button — circular, fixed-position button using border-radius: 50% with a hover lift effect (transform: translateY(-3px))
  • scroll-margin-top: 100px on each .content-section prevents the sticky header from obscuring section headings when an anchor link is clicked

Internal Navigation

The sticky sidebar acts as the internal navigation menu. Each list item links to a section using href="#section-id" anchor syntax. The html { scroll-behavior: smooth; } rule in the global CSS ensures smooth scrolling when these links are clicked. This satisfies the coursework requirement for internal navigation on long content pages.

Content and SDG Relevance

The page topic — sleep and daily lifestyle — is directly relevant to SDG 3 (Good Health and Well-being). Sleep deprivation is a significant but often overlooked contributor to poor health outcomes. The page covers the biological mechanisms behind sleep (circadian rhythm and adenosine build-up), evidence-based health benefits, recommended durations, and actionable tips. All content is original, written by Student 4, and supported by cited academic sources (UpToDate, CDC, PubMed). No content has been reproduced from the UN SDG website.

4. Challenges & Lessons Learned

Challenge 1 — SVG Connector Routing

Drawing connector lines between nodes across four hierarchy levels without them crossing unrelated boxes required careful coordinate planning. Straight <line> elements would have passed through other nodes. The solution was to use <polyline> elements with explicit waypoints — an L-shaped route that moves vertically first, then horizontally, reaching the target node cleanly. Each waypoint coordinate was calculated manually by referencing the node positions in the 860×540 viewBox.

Challenge 2 — JavaScript prompt() Behaviour

The native prompt() function is blocked by default in some mobile browsers when a page is served inside an iframe. It also behaves slightly differently across browsers (some trim whitespace, some do not). This was noted as a known limitation and documented in code comments. The page includes a clear status message after each step confirming what has been saved, so users always have feedback even if a prompt behaves unexpectedly.

Challenge 3 — Reveal Animation Retrigger on Revisit

The CSS @keyframes fadeSlide animation on profile sections only plays when the .revealed class is first added. When a user revisits a step that is already revealed, the class is already present and the animation does not retrigger. Solving this required removing the class, waiting one browser paint cycle using setTimeout(fn, 10), then re-adding it — allowing the browser to register the class removal before re-applying the animation.

Lessons Learned

Planning SVG layouts on paper before writing any code saved significant time. Sketching the four-level hierarchy, estimating node sizes, and labelling approximate coordinates meant that the SVG code could be written with confidence rather than through trial and error. For future projects, I would also consider using CSS custom properties to define the node colours centrally, making theme changes easier.

5. Accessibility Considerations

  • SVG accessibility: The entire <svg> element on the sitemap uses role="img" and a descriptive aria-label. Every clickable node group contains a <title> child element that provides an accessible name for screen readers. All nodes have tabindex="0" so keyboard users can navigate between them using the Tab key, and a visible focus style (orange stroke) is applied via CSS.
  • ARIA live region: The profile status message area uses aria-live="polite", ensuring that assistive technology announces step updates without interrupting whatever the user is currently reading.
  • Progress bar ARIA: The profile progress bar element carries the full set of progressbar ARIA attributes — role="progressbar", aria-valuenow, aria-valuemin="0", and aria-valuemax="100" — all updated dynamically as the user completes steps.
  • Alternative text: Every image on all three pages includes a descriptive alt attribute explaining the image content in context. Purely decorative elements use alt="" where appropriate.
  • Semantic HTML: Landmark elements (<header>, <nav>, <main>, <footer>, <article>, <section>, <aside>) are used throughout to give the page a clear, navigable structure for screen reader users.
  • Colour contrast: The sitemap uses white text on the green and orange node fills throughout. The global colour palette defined in style.css was checked to ensure sufficient contrast between text and background colours across all pages.
  • Keyboard navigation: All interactive elements (navigation links, buttons, profile step buttons, sitemap nodes, sidebar links) are reachable and operable using the keyboard alone.
Native browser prompt() dialogs (used on the profile page) are inherently accessible as they are managed by the browser, not custom HTML. They support keyboard input and are announced correctly by screen readers. The Cancel option is always available to skip any prompt without penalty.

JANET (the Joint Academic Network) sets regulations for the responsible and ethical publication of web pages within UK higher education institutions. The pages I implemented comply with these requirements in the following ways:

  • Original content: All text on my three pages is original and written by me. Where external sources are referenced (e.g. CDC, UpToDate, NHS), they are cited in the References section and linked to the original source. No content has been reproduced verbatim from the UN SDG website or any other source.
  • Responsible use of images: All images used are royalty-free, sourced from iStockPhoto as permitted by the coursework brief. References to image sources are included in the Page Editor references list.
  • No data collection: The User Profile page uses native browser prompt() dialogs — no data is stored server-side, transmitted, or persisted beyond the current browser session. This ensures compliance with data protection principles.
  • No third-party templates: The SVG sitemap was written entirely from scratch by me. No pre-made navigation templates, JavaScript libraries, or downloaded CSS frameworks were used, in line with the coursework requirements.
  • Academic integrity: All code is my own work. Where techniques were learned from lecture notes or MDN Web Docs, this is acknowledged in the References section.
  • Appropriate content: All page content is relevant, professional, and appropriate for an academic web development project. There is no offensive, discriminatory, or misleading material on any of my pages.
